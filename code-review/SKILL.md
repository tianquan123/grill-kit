---

围绕用户给出的固定点，对这次改动做三个维度的评审：

- **Standards（规范）**：代码是否符合本仓库成文的编码规范？
- **Spec（意图）**：代码是否忠实实现了这次改动本来的意图——有设计文档就照它，没有就照对话中商定的范围？
- **质审（质量与风险）**：代码作为代码本身，是不是好代码、有没有坑——潜在缺陷、非法状态、静默失败、测试覆盖缺口？

选定的每条线各跑一个**并行子代理**，以免互相污染上下文；本技能负责汇总它们的发现。简单的改动可以只跑 Standards 与质审两条线（见第 2 步）。每条发现打一个严重度档位（见第 4 步），但档位只在单个维度内部排序用，维度之间刻意不合并、不跨线比胜负（见《为什么是三条线》）。

## 流程

### 1. 定下固定点

用户说的什么就是固定点（commit SHA、分支名、tag、`main`、`HEAD~5` 等）。如果他没指定，就用仓库默认分支的 merge-base，并说明你选了哪个 ref。

评审**改动当前的样子**，无论提交与否。diff 命令一次性确定为 `git diff <fixed-point>`——不带 `...HEAD`，这样暂存区和未提交的编辑都算进去——再配上 `git status --porcelain`，让未跟踪的文件也被点名。当工作已经提交、且你只想要它的提交时，改用 `git diff <fixed-point>...HEAD` 加上 `git log <fixed-point>..HEAD --oneline`。

未跟踪文件不在 `git diff` 里。把它们逐个用 `git diff --no-index /dev/null <file>` 展开，或直接读文件内容，一并交给子代理；只靠 `git status` 点名不算评审。（`--no-index` 有差异时退出码是 1，这是正常的。）

继续之前，先确认固定点能解析（`git rev-parse <fixed-point>`）且改动非空——未跟踪的文件也算内容。坏的 ref 或真正空白的改动应当在这里失败，而不是在两三个并行子代理里面失败。

### 2. 弄清这次改动本来的意图（先定评审深度）

先决定这轮跑几条线。判定是结构性的，用户的话优先：

- **三条线（默认）**：Standards、Spec、质审。
- **两条线（Standards + 质审）**：下面按顺序搜索，设计文档和实施计划**都**命中不了，且改动单点、一眼能看懂它想做什么。用户说「完整评审」一律回三条线；说「简单评审」「只审规范与质量」就直接两条线。拿不准就三条线。
- 两条线跳过 **Spec**：不物化 scope brief、不做下面第 4 条、也不同「这次要交付什么」——那一问只为物化 spec 而存在，没有 Spec 子代理就没有它存在的意义。报告不出现 `## Spec` 段，行总结里写明「本次未跑 Spec」。

按以下顺序寻找意图的原始表述：

1. 用户作为参数传入的路径。
2. `docs/specs/` 下与分支名或特性名匹配的**设计文档**——意图的权威表述。带**验收清单**时最有用：每一项都成为一行评审结论。
3. `docs/plans/` 下的**实施计划**：它说这次按什么顺序做、做到哪一步、哪些任务还没完成。它从设计文档论证而来，两者冲突时以设计文档为准，并且把冲突本身报出来。
4. 对话：与用户商定的范围，以及你要触碰区域的 ADR 中记录的决策。

`CONTEXT.md` 是**词汇与不变量**的来源，不是意图来源。用它来给报告里的东西命名；绝不要把它读成「当初要求了什么」的陈述。

第 4 条需要被**物化**，因为子代理看不见这段对话。当你退回到它时，先写一份简短的 **scope brief（范围简报）**——商定的行为、约束它的决策、以及明确排除的东西——然后把这段文字当作 spec 传给 Spec 子代理。**第 4 条与「四条落空就问用户」只在三条线评审下执行**——两条线没有 Spec 子代理，这两步直接跳过。

### 3. 找出规范来源

按这个顺序找，**上层优先，但五层都要读**：

1. 仓库根目录的**代理指引文件**：`AGENTS.md`、`CLAUDE.md`、`.github/copilot-instructions.md`。
2. 仓库根的 **`CONSTRAINTS.md`**（质量门）：这个仓库「绿」的定义——命令、底线。
3. 仓库自述的规范文件：`CONTRIBUTING.md`、`CODING_STANDARDS.md`，以及 `docs/` 下同类的文件。
4. **上面这些文件链接出去的规范文档。** 根目录的指引常常只是一张索引，真正的规则在它指向的表和约定里。**跟进去读。**
5. `docs/adr/` 里落在本次改动范围内的决策：ADR 记的是「为什么这么选」，违反它就是违反这个仓库自己的意图。

这几层里凡是**硬性、可判定**的规则——分层不许越级、某类文件禁止手工修改、两处定义必须同步、必填的字段或注释头——都比坏味道重要得多。它们才是 Standards 维度的主要产出。

五层全部落空时，才去读 [BASELINE.md](BASELINE.md) 兜底——仓库有成文规范时不必读它。

### 4. 并行起子代理（数量随第 2 步的深度）

三条线就全跑，两条线就跑 Standards 与质审、Spec 简报不写。每个子代理各有一个明确的**狩猎清单**——不是「有什么报什么」，而是先知道这次要去找什么。每条发现的严重度档位：

- **CRITICAL**：潜在 bug 可能造成生产事故或数据损坏 → 立即处理。
- **HIGH**：迟早会炸的 bug、关键测试缺失 → 当前迭代处理。
- **MEDIUM**：技术债累积、可维护性下降 → 排期处理。
- **LOW**：小改进、性能优化 → 顺带处理。
- **INFO**：观察、正面模式 → 无需动作。

档位只用于**单个维度内部**的排序，不跨维度比较。

**Standards 子代理的提示词**应包含：

- 完整的 diff 命令；未跟踪文件的展开命令或文件列表；改动已提交时再附上提交列表。
- 你在第 3 步找到的规范来源：**文件路径 + 你需要它遵守的具体条款**。指引文件往往很长，把相关那几条摘出来给它，比丢一个路径有用。
- 只有当仓库没有任何成文规范时，才把 [BASELINE.md](BASELINE.md) 的内容粘贴给它（子代理看不到这份技能文档，也读不到那个文件）。
- 简报：「按文件/按 hunk 汇报：(a) diff 中每一处违反成文规范的地方：引用那条规范（文件 + 规则）；其中**新增的抑制注释、跳过的测试、被删的断言、被改动的阈值**按硬性违规处理，逐条点名；(b) 你发现的任何基线坏味道：点名并引用该 hunk。区分硬性违规与判断：成文规范的违反可以是硬性的，但基线坏味道永远是判断，且仓库成文规范优先于基线。工具能管的一律跳过。把发现按 CRITICAL→HIGH→MEDIUM→LOW→INFO 分档，排在该档位下（CRITICAL=可能造成生产事故或数据损坏；HIGH=迟早会炸的 bug 或关键测试缺失；MEDIUM=技术债累积；LOW=小改进；INFO=观察）。400 字以内。」

**Spec 子代理的提示词**应包含：

- diff 命令；未跟踪文件的展开命令或文件列表；改动已提交时再附上提交列表。
- spec 本身：要么是某文件的路径与内容，要么是你第 2 步写的 **scope brief** 全文粘贴（子代理没有别的途径拿到它）。
- 简报：「汇报：(a) 要求过、但缺失或只做了一半的需求；(b) diff 里没被要求过的行为（范围蔓延）；(c) 看起来实现了、但实现不对的需求。当来源带验收清单时，**逐项**给一行结论——完成、部分完成、缺失、或做错了——并引用该项。否则引用每条发现背后的 spec 或 scope brief 原文。把发现按 CRITICAL→HIGH→MEDIUM→LOW→INFO 分档（含义见 Standards 简报）。400 字以内。」

**质审子代理的提示词**应包含：

- diff 命令；未跟踪文件的展开命令或文件列表；改动已提交时再附上提交列表。
- 狩猎清单（全文粘贴，子代理看不到这份技能文档）：按优先序只审这六类，**成文规范的违反归 Standards、基线坏味道归基线、被规格点名归 Spec，一律不重复报**：

  1. **潜在 bug 与逻辑风险**：边界条件、状态管理、并发 / 异步陷阱。
  2. **类型安全与不变量缺口**：非法状态可被表达、未验证的边界。
  3. **可观测性与诊断缺口**：静默失败、吞异常、日志缺口。
  4. **韧性与容错**：超时、重试、资源泄漏、事务缺口。
  5. **测试质量与覆盖缺口**：本次改动自己的风险有没有被测试覆盖。被删的断言、被跳过的测试、被改动的阈值是硬性违规，归 Standards 点名，这里只评覆盖。
  6. **安全与性能**：只升级会导致数据丢失 / 宕机的级别（鉴权缺口、注入、N+1），越级的记下来告诉用户。

  其余维度（清晰度、模块化、文档、演进）只在明显到妨碍理解时补一句，不主动去抓。
- 简报：「按 CRITICAL→HIGH→MEDIUM→LOW→INFO 汇报质审下的缺陷与风险，每条注明 file:line 并点出它触发的具体陷阱（如『这里并发下会丢状态』）；只报规范与意图都覆盖不到的质量与风险。没有发现就写『无』（含义见 Standards 简报）。400 字以内。」

### 5. 汇总

把选定的线对应的报告分别放在 `## Standards`、`## Spec`、`## 质审` 标题下呈现（两条线评审没有 `## Spec` 段），原文照录或稍作清理，并用 `CONTEXT.md` 的词汇命名领域概念。**不要**合并或重排这些发现——尤其是不要按严重度跨维度挑出唯一的赢家，那正是这套分离要防止的重排（见《为什么是三条线》）。

最后给一行总结：本次的**意图来源**是哪一条（设计文档或计划请给出路径；如果退回成了会话简报，就写明「本次没有文档」；两条线评审再写明「本次未跑 Spec」），每条线的发现总数，如果意图来源带验收清单还有**仍未完成的清单项**，以及*每条线内部*最严重的问题（如果有）。让缺失的文档在报告里可见。

### 6. 评审之后

报告交出去之后，就轮到**接收**这一半。发现清单不是命令清单。

**先验证，再动手：**

1. **读完**全部反馈再动手。
2. **复述**：把每条要求用自己的话讲一遍，或者直接问。
3. **对照代码现实核对**：这条反馈对着当前代码成立吗？改动者当时为什么那么写？
4. **判断**：对**这个仓库**来说，技术上站得住吗？
5. **回应**：技术性的确认，或者有理有据的反驳。
6. **实施**：一次一条，每条改完就验证。

**该说的话长这样**：复述技术要求、问不清楚的条目、给出带证据的反驳——或者直接开始动手。表态不值钱，动作才值钱。（硬护栏：附和不是回应。）

**不清楚就先问。** 清单里只要有一条没看懂，就先问清楚再动手——条目之间常常相关，理解一半就会改错一半。

**该反驳就反驳。** 评审也会错。反驳要带技术理由和证据（代码、验证输出）。**但反驳之后，如果对方坚持，就按对方的判断走**——决策权在他手上。

**越界的发现不进这一轮。** 评审顺手提的、不属于本次范围的改进，记下来告诉用户。

## 坏味道基线

**只在仓库没有任何成文规范时读它**：[BASELINE.md](BASELINE.md)。仓库有成文规范时，上面五层才是 Standards 维度的主体，基线只是兜底。

## 为什么是三条线

一次改动可能通过一条线而通不过另一条：

- 代码符合每一条规范，但实现的是错误的东西 → **Standards 过，Spec 挂。**
- 代码做的正是被要求的事，但破坏了项目的约定 → **Spec 过，Standards 挂。**
- 代码既合规范又合意图，但本身就是颗雷——边界会炸、失败会静默、关键路径没测试 → **Standards 过、Spec 过，质审挂。**

分开汇报，可以防止一条线掩盖另一条线。严重度档位只在单条线内部比较：跨线比较会重新引入这条线之间要防止的重排。

两条线评审是**成本决策**，不是把 Spec 并入别处——它舍的是「一个独立子代理该有的狩猎」，不是「做没做对」这回事本身：简单任务里意图靠审的人一眼看穿，不需要为它单开一个子代理。改动一大、或有了设计文档和计划，就回三条线。这符合全格的底线：**随任务简单而缩水的是产出物，永远不是批准。**
