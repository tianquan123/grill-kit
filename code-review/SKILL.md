围绕用户给出的固定点，对这次改动做两轴评审：

- **Standards（规范）**：代码是否符合本仓库成文的编码规范？
- **Spec（意图）**：代码是否忠实实现了这次改动本来的意图——有设计文档就照它，没有就照对话中商定的范围？

两轴各跑一个**并行子代理**，以免互相污染上下文；本技能负责汇总它们的发现。

## 流程

### 1. 定下固定点

用户说的什么就是固定点（commit SHA、分支名、tag、`main`、`HEAD~5` 等）。如果他没指定，就用仓库默认分支的 merge-base，并说明你选了哪个 ref。

评审**改动当前的样子**，无论提交与否。diff 命令一次性确定为 `git diff <fixed-point>`——不带 `...HEAD`，这样暂存区和未提交的编辑都算进去——再配上 `git status --porcelain`，让未跟踪的文件也被点名。当工作已经提交、且你只想要它的提交时，改用 `git diff <fixed-point>...HEAD` 加上 `git log <fixed-point>..HEAD --oneline`。

继续之前，先确认固定点能解析（`git rev-parse <fixed-point>`）且改动非空——未跟踪的文件也算内容。坏的 ref 或真正空白的改动应当在这里失败，而不是在两个并行子代理里面失败。

### 2. 弄清这次改动本来的意图

按以下顺序寻找意图的原始表述：

1. 用户作为参数传入的路径。
2. `docs/specs/` 下与分支名或特性名匹配的**设计文档**——意图的权威表述。带**验收清单**时最有用：每一项都成为一行评审结论。
3. `docs/plans/` 下的**实施计划**：它说这次按什么顺序做、做到哪一步、哪些任务还没完成。它从设计文档论证而来，两者冲突时以设计文档为准，并且把冲突本身报出来。
4. 对话：与用户商定的范围，以及你要触碰区域的 ADR 中记录的决策。

`CONTEXT.md` 是**词汇与不变量**的来源，不是意图来源。用它来给报告里的东西命名；绝不要把它读成「当初要求了什么」的陈述。

第 4 条需要被**物化**，因为子代理看不见这段对话。当你退回到它时，先写一份简短的 **scope brief（范围简报）**——商定的行为、约束它的决策、以及明确排除的东西——然后把这段文字当作 spec 传给 Spec 子代理。

四条都落空时，问用户一个问题：这次改动要交付什么？他的回答就成为简报。

### 3. 找出规范来源

按这个顺序找，**先找到的赢**：

1. 仓库根目录的**代理指引文件**：`AGENTS.md`、`CLAUDE.md`、`.github/copilot-instructions.md`。
2. 仓库根的 **`CONSTRAINTS.md`**（质量门）：这个仓库「绿」的定义——命令、底线、谁检查。
3. 仓库自述的规范文件：`CONTRIBUTING.md`、`CODING_STANDARDS.md`，以及 `docs/` 下同类的文件。
4. **上面这些文件链接出去的规范文档。** 根目录的指引常常只是一张索引，真正的规则在它指向的表和约定里。**跟进去读。**
5. `docs/adr/` 里落在本次改动范围内的决策：ADR 记的是「为什么这么选」，违反它就是违反这个仓库自己的意图。

这几层里凡是**硬性、可判定**的规则——分层不许越级、某类文件禁止手工修改、两处定义必须同步、必填的字段或注释头——都比坏味道重要得多。它们才是 Standards 轴的主要产出。

五层全部落空时，才去读 [BASELINE.md](BASELINE.md) 兜底——仓库有成文规范时不必读它。

### 4. 并行起两个子代理

**Standards 子代理的提示词**应包含：

- 完整的 diff 命令；改动已提交时再附上提交列表。
- 你在第 3 步找到的规范来源：**文件路径 + 你需要它遵守的具体条款**。指引文件往往很长，把相关那几条摘出来给它，比丢一个路径有用。
- 只有当仓库没有任何成文规范时，才把 [BASELINE.md](BASELINE.md) 的内容粘贴给它（子代理看不到这份技能文档，也读不到那个文件）。
- 简报：「按文件/按 hunk 汇报：(a) diff 中每一处违反成文规范的地方：引用那条规范（文件 + 规则）；其中**新增的抑制注释、跳过的测试、被删的断言、被改动的阈值**按硬性违规处理，逐条点名；(b) 你发现的任何基线坏味道：点名并引用该 hunk。区分硬性违规与判断：成文规范的违反可以是硬性的，但基线坏味道永远是判断，且仓库成文规范优先于基线。工具能管的一律跳过。400 字以内。」

**Spec 子代理的提示词**应包含：

- diff 命令；改动已提交时再附上提交列表。
- spec 本身：要么是某文件的路径与内容，要么是你第 2 步写的 **scope brief** 全文粘贴（子代理没有别的途径拿到它）。
- 简报：「汇报：(a) 要求过、但缺失或只做了一半的需求；(b) diff 里没被要求过的行为（范围蔓延）；(c) 看起来实现了、但实现不对的需求。当来源带验收清单时，**逐项**给一行结论——完成、部分完成、缺失、或做错了——并引用该项。否则引用每条发现背后的 spec 或 scope brief 原文。400 字以内。」

### 5. 汇总

把两份报告分别放在 `## Standards` 和 `## Spec` 标题下呈现，原文照录或稍作清理，并用 `CONTEXT.md` 的词汇命名领域概念。**不要**合并或重排这些发现，因为两轴是刻意分开的（见《为什么是两轴》）。

最后给一行总结：本次的**意图来源**是哪一条（设计文档或计划请给出路径；如果退回成了会话简报，就写明「本次没有文档」），每轴的发现总数，如果意图来源带验收清单还有**仍未完成的清单项**，以及*每一轴内部*最严重的问题（如果有）。让缺失的文档在报告里可见。不要在跨轴之间挑出唯一的赢家：那正是这套分离要防止的重排。

### 6. 评审之后

报告交出去之后，就轮到**接收**这一半。发现清单不是命令清单。

**先验证，再动手：**

1. **读完**全部反馈再动手。
2. **复述**：把每条要求用自己的话讲一遍，或者直接问。
3. **对照代码现实核对**：这条反馈对着当前代码成立吗？改动者当时为什么那么写？
4. **判断**：对**这个仓库**来说，技术上站得住吗？
5. **回应**：技术性的确认，或者有理有据的反驳。
6. **实施**：一次一条，每条改完就验证。

**该说的话长这样**：复述技术要求、问不清楚的条目、给出带证据的反驳——或者直接开始动手。表态不值钱，动作才值钱。（硬护栏：附和不是回应。）

**不清楚就先问。** 清单里只要有一条没看懂，就先问清楚再动手——条目之间常常相关，理解一半就会改错一半。

**该反驳就反驳。** 评审也会错。反驳要带技术理由和证据（代码、验证输出）。**但反驳之后，如果对方坚持，就按对方的判断走**——决策权在他手上。

**越界的发现不进这一轮。** 评审顺手提的、不属于本次范围的改进，记下来告诉用户。

## 坏味道基线

**只在仓库没有任何成文规范时读它**：[BASELINE.md](BASELINE.md)。

仓库有成文规范时不需要读——那四层才是 Standards 轴的主体，基线只是兜底。

## 为什么是两轴

一次改动可能通过一轴而通不过另一轴：

- 代码符合每一条规范，但实现的是错误的东西 → **Standards 过，Spec 挂。**
- 代码做的正是被要求的事，但破坏了项目的约定 → **Spec 过，Standards 挂。**

分开汇报，可以防止一轴掩盖另一轴。
