# 代码库设计

设计**深模块（deep module）**：把大量行为藏在一个小接口后面，放在一条干净的接缝上，并通过那个接口可测。凡是代码正在被设计或重构的地方，都用这套语言和这些原则。目标是给调用方**杠杆（leverage）**、给维护者**局部性（locality）**、给所有人可测性。

## 术语表

严格使用这些术语：不要替换成"组件""服务""API""边界"。语言一致就是全部意义所在。

**模块（Module）**：任何拥有接口和实现的东西。刻意与尺度无关：一个函数、一个类、一个包，或一条横跨多层的切片。_避免_：unit、component、service。

**接口（Interface）**：调用方为了正确使用这个模块所必须知道的一切：类型签名，还有不变量、顺序约束、错误模式、必需的配置、以及性能特征。_避免_：API、signature（太窄，这两个只指类型层面的表面）。

**实现（Implementation）**：模块内部的东西，它的代码本体。与**适配器（Adapter）**区分开：一个东西可以是"小适配器 + 大实现"（一个 Postgres 仓储），也可以是"大适配器 + 小实现"（一个内存假件）。当话题是接缝时用"适配器"，否则用"实现"。

**深度（Depth）**：接口上的杠杆。调用方（或测试）每学一单位接口，能行使多少行为。当大量行为待在一个小接口后面时，模块是**深的**；当接口几乎和实现一样复杂时，它是**浅的**。

**接缝（Seam）** _(Michael Feathers)_：一个你无需改动此处就能改变行为的地方；也是模块接口所**坐落的位置**。接缝放哪里本身就是一项设计决策，与"接缝后面放什么"是两回事。_避免_：boundary（与 DDD 的限界上下文 bounded context 撞词）。

**适配器（Adapter）**：在一条接缝上满足某个接口的具体东西。描述的是**角色**（它填哪个槽），不是**实质**（里面是什么）。

**杠杆（Leverage）**：调用方从深度中得到的东西。每学一单位接口，换来更多能力。一份实现，回报 N 个调用点和 M 个测试。

**局部性（Locality）**：维护者从深度中得到的东西。改动、bug、知识、验证集中在一处，而不是散布到各调用方。修一次，处处已修。

## 深 vs 浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│      小 接 口        │  ← 方法少、参数简单
├─────────────────────┤
│                     │
│     深 实 现         │  ← 复杂逻辑被藏起来
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 很少实现（避免）：

```
┌─────────────────────────────────┐
│          大 接 口                │  ← 方法多、参数复杂
├─────────────────────────────────┤
│        薄 实 现                  │  ← 只是转发
└─────────────────────────────────┘
```

设计接口时问自己：

- 我能减少方法的数量吗？
- 我能简化参数吗？
- 我能把更多复杂度藏进去吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部可以由许多小的、可 mock 的、可替换的零件组成；它们只是不属于接口。模块可以同时拥有**内部接缝**（对实现私有，供它自己的测试使用）和位于接口处的**外部接缝**。
- **删除检验（deletion test）。** 设想把这个模块删掉。如果复杂度随之消失，它就是个直通件；如果复杂度在 N 个调用方那里重新出现，它就挣到了自己的位置。
- **接口就是测试面。** 调用方和测试跨越同一条接缝。如果你想**绕过**接口去测，那多半是模块形状不对。
- **一个适配器意味着假想的接缝，两个适配器才意味着真实的接缝。** 除非真有东西在这条接缝上发生变化，否则不要引入接缝。

## 为可测性而设计

好的接口让测试变得自然：

1. **接受依赖，不要创建依赖。**

   ```typescript
   // 可测
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面面积要小。** 方法越少，需要的测试越少；参数越少，测试准备越简单。

## 关系

- 一个**模块**恰好有一个**接口**（它呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，相对于它的**接口**来衡量。
- **接缝**是**模块**的**接口**所坐落的地方。
- **适配器**坐在一条**接缝**上，满足那个**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**局部性**。

## 被否掉的表述

- **把深度当成"实现行数 ÷ 接口行数"的比值**（Ousterhout）：这会奖励往实现里灌水。我们改用"深度即杠杆"。
- **把 Interface 当成 TypeScript 的 interface 关键字或类的公开方法**：太窄；这里的接口包含调用方必须知道的所有事实。
- **Boundary**：与 DDD 的限界上下文撞词。请说**接缝**或**接口**。
