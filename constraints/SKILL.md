# 质量底线：写下来，守住它

**核心原则：收紧是静默的，放松必须出声。**

链上其它技能管「做出来的东西好不好」：`tdd` 管测试怎么写，`code-review` 管代码读起来对不对，`verification` 管结论有没有证据。**没有一条管「这个仓库的『绿』是什么意思」，也没有一条拦得住把门槛调低换来的绿。**

这个技能补的就是这一环：一个写下来的文件，加一套对 diff 的核对。它不写脚本——五个动作用 `git diff` 加眼睛就能过。

## 什么时候用

- 仓库没有成文的质量门——没有任何地方写清楚「跑什么、过了算绿」
- 要跑构建、测试、静态检查，或者要声称「通过」
- **有人在动测试、动阈值、加抑制注释**——包括你自己

**不用走首次创建流程**：试验档（产出是答案，不是要留下来的代码）；一次性脚本；仓库已经有 `CONSTRAINTS.md`。已有文件时**照它走，不要重写，也不要顺手整理它**；但下面的五个放松动作照跑。

## 第一次用：先发现，后提问

**能读到的不要问。** 先看构建文件与 CI：`pom.xml` / `build.gradle`、`.github/workflows/`、现有测试目录、已有的静态检查配置。把你看到的用两行报出来，再只问剩下的那一个：哪些维度你要真的拦下来。

然后写 `CONSTRAINTS.md` 到仓库根，**只写两段**。

## 五个放松动作

**这是本技能真正的机制。** 声称通过之前，对着这次 diff 逐条过一遍：

| 动作 | 长什么样 | 怎么看 |
|---|---|---|
| **阈值被调低** | 覆盖率门槛变小、超时变长、排除项变多 | 跟改前比。**带方向的数字**（不小于 / 不超过）朝松的那边改，就是放松 |
| **测试被改简单** | 新增 `.skip`、测试文件被删、断言被删但测试还在 | 看删除的行。删掉一条 `assert` 就是拆掉一道门 |
| **检查被静音** | 新增一条抑制注释、CI 里加 `continue-on-error` | 抑制注释只在**放松**时有意义，收紧用不到它 |
| **活没干完** | 抛未实现的桩、空 `catch`、占位 `TODO` | 空 `catch` 是把失败改成沉默 |
| **冒出新例外** | 排除清单多一行、规则多一条豁免 | 例外要有理由和期限，写在文件里 |

**这五个动作里有任何一个，就不是「通过」。** 停下来，把「放松了什么、为什么、错了的代价是什么」摆给用户，让他拍板。

**收紧是静默的**：加测试、加断言、把阈值收紧，不用报告。

## Java · Spring 的清单

模式是本技能**唯一跟栈有关**的部分。换栈只改这张表，判定逻辑不动。

- **静音检查器**：`@SuppressWarnings`、`// NOPMD`、`// CHECKSTYLE:OFF`、`@SuppressFBWarnings`、新增 Sonar 排除项
- **测试变简单**：`@Disabled`、`@Ignore`、`assertTrue(true)`、删断言、测试里的空 `catch`
- **跳过测试**：`<skipTests>`、`-DskipTests`、`-Dmaven.test.failure.ignore=true`、新增 surefire `excludes`、Gradle `test { enabled = false }`
- **CI 面**：`continue-on-error: true`、`if: always()`、`|| true`、`--no-verify`
- **半成品**：`throw new UnsupportedOperationException("TODO")`、空 `catch {}`、只写签名不写实现

## CONSTRAINTS.md 模板

<constraints-template>

```markdown
# Constraints

## 底线（每个改动都过）

- 不许为让改动变绿而放松本文件
- 不许新增抑制注释（@SuppressWarnings / // NOPMD / // CHECKSTYLE:OFF）
- 不许新增跳过的测试（@Disabled / @Ignore / -DskipTests / surefire excludes）
- 不许删测试或删断言；要删，先停下来报给用户
- 不许留半成品（未实现的桩、空 catch、占位 TODO）
- 源码里不许出现密钥/凭据
- 外部输入必须校验

## 命令（这就是「绿」的定义）

| 检查 | 命令 | 什么时候跑 |
|---|---|---|
| 编译 | `<本仓库实际的那条>` | 每次改完 |
| 测试 | `<本仓库实际的那条>` | 每个任务收尾 |
| 静态检查 | `<本仓库实际的那条>` | 每个任务收尾 |
```

</constraints-template>

**每一行必须写出产生判定的那条命令。有数字没有命令 = 愿望，不是约束。**

仓库根本没有可跑的命令时，**明说没有自动化验证**，走 `verification` 的降级路径。不要在 `CONSTRAINTS.md` 里写一条跑不起来的命令——那等于递给 `verification` 一份假证据（见 `tdd` 的「没有测试基建的时候」）。

**质量只能收紧**：没有目标数字，就记录**今天的值**，只许不变差。设一个今天达不到的门槛，只会得到一个永远红的构建，然后所有人学会无视红色。

## 谁在哪一步用它

- **`implement`**：每个任务收尾、跑验证项之前，过五个放松动作。**任务完成的判据里没有「放松底线」这条路。**
- **`verification`**：关卡检查第一步「指名」——指的那条命令应当来自命令表。表里没有，就先补上再谈验证。
- **`code-review`**：Standards 维度的规范来源之一。新增的抑制注释、跳过的测试、被改动的阈值，按硬性违规处理；质审维度补的是规范管不到的「代码本身是不是雷」。

前两个是**第一道网**（跑绿那一刻就拦），`code-review` 是第二道。

## Red Flags

| 念头 | 现实 |
|---|---|
| 「测试红了，加个 @Disabled 就绿了」 | 那是改底线，不是改代码 |
| 「先调低阈值，回头再补」 | 回头不存在，阈值已经写进文件里了 |
| 「这条命令跑不起来，先写上去」 | 写一条跑不起来的命令 = 给 `verification` 一份假证据 |
| 「这个例外就这一次」 | 例外要有理由和期限，写进文件 |
| 「数字我随手定一个」 | 定一个今天达不到的数字，等于教所有人无视红色 |
| 「阈值改小一点，差别不大」 | 差别大不大不由改的人判断 |
| 「仓库里有 CONSTRAINTS.md，我顺手整理一下」 | 照它走。动它就是放松，走上面的流程 |
| 「删掉这个测试它就绿了」 | 删测试是放松动作里最贵的一种，必须停下来问 |
