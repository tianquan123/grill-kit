# 调试：先根因，后修复

**核心原则：没有找到根因之前，不许提修复方案。**

## 铁律

```
先查清为什么，再动手改什么。
```

**随机改动 + 症状消失 = 你并不知道自己修好了没有。**

## 四阶段

### 阶段 1：根因调查

- **读完整的错误信息。** 不是扫一眼，是读完。栈顶那一行往往不是原因。
- **稳定复现。** 能稳定复现的 bug 是好 bug；不能复现，就先解决复现。
- **看它最近变了什么**：版本历史里最近的改动、配置、依赖、环境。
- **在边界上取证**：数据进来的地方、出去的地方、两段代码交界的每一个接缝，看实际值。
- **一路往回追**：从症状点往上追到**第一个不对的地方**。第一个不对的地方才是根因，它下游的全是后果。

### 阶段 2：模式分析

- 这个仓库里**同类东西是怎么写的**？找一个能正常工作的同类实现，逐项比差异——差异清单就是嫌疑犯清单。
- 别的调用方会不会踩同一个坑？

### 阶段 3：假设与验证

- 写下一个**可证伪的**假设：「如果 X 是原因，那么 <某条命令 / 某个观察> 会是这样。」
- **一次只验一条。** 同时改三处再观察 = 什么也没学到。
- 假设错了就记下来（免得绕回同一个坑），换下一个。

### 阶段 4：实现

- 先写一个**能复现原症状的验证**，看它失败。
- 修**根因**，不是修症状。
- 看它通过。
- 再去找**同一个根因的其它出口**——一个 bug 很少只有一个出口。
- 过 `verification`：没有新鲜证据，不许说修好了。

## 与流程的关系

调试是**旁路**，不是流程里的一档。定位到具体缺陷之后，**再对「修它」这件事定一次档**：改的是已经存在的一段流程 → 局部；要动结构或者新建 → 架构。

调试期间**不要顺手重构**。只留修复，以及能防它复发的验证。

## Red Flags —— 出现就停下，回到阶段 1

- 「先改一下试试看」——试什么？假设是什么？
- 「大概是因为 X 吧」——大概不是证据
- 一次改好几处
- 症状消失了就宣布修好
- 开始加兜底、加空值判断、把报错压掉，来「绕开」问题
- 追了三十分钟，一直在换地方看，却没写下任何一个假设

## 合理化对照表

| 借口 | 现实 |
|---|---|
| 「问题太简单，不用走流程」 | 简单的是根因，不是症状 |
| 「时间紧，先止血」 | 没找到根因的修复会以更大的代价回来 |
| 「先加个兜底把报错压掉」 | 那是把根因藏起来，不是修它 |
| 「我改的这几处，总有一处是对的」 | 那就是一次改三处，什么也没学到 |
| 「改完之后症状没了」 | 证明它不会在别的路径上再出来，才算 |
