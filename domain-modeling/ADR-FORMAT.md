# ADR 格式

ADR 放在 `docs/adr/`，顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

按需创建 `docs/adr/` 目录：只在第一条 ADR 需要时才建。

## 模板

```md
# {决策的简短标题}

{1–3 句话：背景是什么、我们决定了什么、为什么。}
```

就这样。一条 ADR 可以只有一个段落。价值在于记录**做过这个决定**以及**为什么**，而不在于把章节填满。

## 可选章节

只在确实增值时才加。多数 ADR 都不需要。

- **Status 前置元数据**（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策会被重新审视时有用
- **Considered Options（考虑过的选项）**：只有被否掉的方案值得记住时才加
- **Consequences（后果）**：只有非显而易见的下游影响需要点明时才加

## 编号

扫描 `docs/adr/` 里已有的最大编号，加一。

## 什么时候提议 ADR

判据见 [SKILL.md](SKILL.md) 的「克制地提议 ADR」：难以逆转、没有背景会让人意外、是真实取舍的结果，三条必须同时成立。本文只管格式。

### 什么算数

- **架构形态。** "我们用 monorepo。""写模型是事件溯源的，读模型投影进 Postgres。"
- **上下文之间的集成方式。** "Ordering 与 Billing 通过领域事件通信，而不是同步 HTTP。"
- **带锁定效应的技术选型。** 数据库、消息总线、认证服务商、部署目标。不是每个库：只是那些换掉要花一个季度的。
- **边界与范围决策。** "客户数据归 Customer 上下文所有；其他上下文只按 ID 引用它。"明确说出的"不做"和"做"同样有价值。
- **刻意偏离常规做法。** "我们用裸 SQL 而不是 ORM，因为 X。"任何合理读者会假设相反的场合。这些能阻止下一位工程师去"修好"一个本来就是刻意的设计。
- **代码里看不见的约束。** "因为合规要求我们不能用 AWS。""因为合作方 API 合约，响应时间必须低于 200ms。"
- **被否掉的替代方案（当否掉的理由不显而易见时）。** 如果你考虑过 GraphQL 却因微妙理由选了 REST，记下来；否则半年后有人会再提一次 GraphQL。
