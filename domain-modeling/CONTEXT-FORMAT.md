# CONTEXT.md 格式

## 结构

```md
# {上下文名称}

{一到两句话，说明这个上下文是什么、为什么存在。}

## 术语

**Order（订单）**：
{一到两句话的术语说明}
_避免_：Purchase、Transaction

**Invoice（发票）**：
交付后向客户发出的付款请求。
_避免_：Bill、Payment Request

**Customer（客户）**：
提交订单的个人或组织。
_避免_：Client、Buyer、Account

## 不变量

- 订单金额永远为正；为零或负的下单必须被拒绝
- 订单一旦进入 Cancelled，不可回到任何其他状态
- 只有已交付的订单才会产生 Invoice
```

## 规则

### 术语（`## 术语`）

- **要有主见。** 同一个概念有多个词时，挑最好的那个，其余列进 `_Avoid_`。
- **定义要紧。** 最多一到两句。定义它**是什么**，不是它**做什么**。
- **只收本项目上下文特有的术语。** 通用编程概念（超时、错误类型、工具类模式）不属于这里，哪怕项目里用得再多。加一个术语之前先问：这是本上下文独有的概念，还是通用编程概念？只有前者属于这里。
- 出现自然的聚类时，**把术语分到子标题下**；所有术语都属于同一个内聚领域时，平铺一份列表也行。

### 不变量（`## 不变量`）

- **只收永远成立、与实现无关的领域规则。** 写出来应当是**这个领域的定义性事实**，而不是"这次功能怎么做"。测试："把整个实现换掉之后，这句话还成立吗？"不成立就不属于这里。
- **每条一句话，可判定。** 一眼能看出违反没违反（"金额永远为正"是，而"金额要合理"不是）。
- **说规则本身，不解释原因。** 原因若值得记，那是 ADR 的事。
- **技术约束不进这里。** 性能指标（"响应 <200ms"）、合规限制（"不能用 AWS"）、选型锁定 —— 这些是决策，去 `docs/adr/`。判据：业务规则不变、只换技术栈时，这条规则会消失吗？会，就去 ADR。
- **需求不进这里。** "这次要支持部分取消"是需求，去 `docs/specs/<slug>.md`。
- 没有不变量时，整段省略。

## 单上下文 vs 多上下文仓库

**单上下文（多数仓库）：** 仓库根目录一个 `CONTEXT.md`。

**多上下文：** 根目录的 `CONTEXT-MAP.md` 列出各个上下文、它们在哪里、以及彼此的关系：

```md
# Context Map（上下文地图）

## 上下文

- [Ordering](./src/ordering/CONTEXT.md)：接收并跟踪客户订单
- [Billing](./src/billing/CONTEXT.md)：生成发票并处理付款
- [Fulfillment](./src/fulfillment/CONTEXT.md)：管理仓库拣货与发货

## 关系

- **Ordering → Fulfillment**：Ordering 发出 `OrderPlaced` 事件；Fulfillment 消费它开始拣货
- **Fulfillment → Billing**：Fulfillment 发出 `ShipmentDispatched` 事件；Billing 消费它生成发票
- **Ordering ↔ Billing**：共享 `CustomerId` 与 `Money` 类型
```

该技能自行推断适用哪种结构：

- 若存在 `CONTEXT-MAP.md`，读它找出各个上下文
- 若只有根 `CONTEXT.md`，即单上下文
- 若两者都没有，在第一个术语确定时按需创建根 `CONTEXT.md`

存在多个上下文时，推断当前话题属于哪一个。判断不出就问。
