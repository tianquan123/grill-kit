# Spring Boot 后端设计指导

这是一套**通用判断框架**，不是要求所有项目采用同一种架构。它也是判断依据，不是流程入口：要动手改代码时，先按 `use-grill` 定档并取得批准。

新代码首先要与项目已有代码保持一致：先理解邻居如何分层、命名、处理异常和事务，再决定
这次代码应住在哪里、承担什么职责。项目已有约定、技术栈特性和用户明确要求优先于本文的
默认原则；如果需要偏离，说明依据、取舍和影响。

## 速览：判断顺序

动手或给出方案前，按这个顺序过一遍（逐条依据见下文各节；完整版见第七节）：

1. **找邻居**——同模块相近代码怎么分层、命名、处理异常和事务（见「一」）。
2. **说清职责**——这段代码主要负责什么、输入输出、副作用（见「二」）。
3. **定边界**——归哪个现有边界，还是确有新边界（见「二」）。
4. **对齐风格**——命名、异常、事务、映射、测试跟着邻居走。
5. **扫风险**——越界、重复副作用、并发、敏感数据、查询规模（见「四」）。
6. **看入口**——写路径是否可读作分步编排、每步由明确的 Service / 工具类 / Client
   承担；读路径 Controller 只做协议、QueryService 取数并组装 VO（见「用例编排」与
   「读用例的形态」）。
7. **算测试账**——规则能不能零 mock 测、用例方法要几个 `given`、有没有隐式时间和
   静态调用挡路（见「三」）。
8. **偏离要出声**——不改默认原则就先讲清为什么、替代方案、代价。

其余各节是这八步的依据，需要时按序号回查。

## 一、先理解项目，再提出方案

动手或给出重构建议前，尽量用项目已有代码回答：

1. **项目如何分层** —— 包结构、模块边界和调用方向是什么；不要凭经验臆造目录。
2. **同类职责住在哪里** —— 找相近的 Controller、Service、Mapper、Client、DTO 等邻居。
3. **邻居如何实现** —— 观察命名、返回体、异常、日志、事务、参数校验、映射和测试方式。
4. **哪些是项目约定，哪些只是历史遗留** —— 不要盲目复制明显的越界或重复问题。

优先查看同模块的相近代码；没有直接邻居时，再查其他模块、测试、构建配置、CI 和文档。
仍然缺少证据且答案会影响设计时，提出一个具体问题，而不是自行发明一套架构。

“找邻居”的目的不是照抄某个类，而是识别项目的设计语言，并判断这次需求是否应该沿用它。

## 二、按职责和边界判断该由谁负责

按“这段代码主要负责什么”判断，而不是按表名、文件大小或个人偏好判断。

| 主要职责 | 通常由谁负责 | 应负责的事情 | 常见越界信号 |
|---|---|---|---|
| 处理外部 HTTP / RPC 协议 | Controller / Endpoint | 接收参数、入口校验、调用用例、转换响应 | 业务规则、SQL、事务、直接调用第三方 |
| 表达一个业务用例或流程 | Service / Use Case / Application Service | 编排步骤、业务规则、事务和跨能力协作 | 变成单表 CRUD 杂物间，或只做无意义转发 |
| 访问持久化系统 | Repository / Mapper / DAO | 查询、保存、更新和持久化映射 | 业务状态判断、跨模块流程、权限决策 |
| 连接第三方、缓存、消息或文件系统 | Client / Gateway / Adapter | 协议适配、调用、结果转换和基础设施错误处理 | 业务层直接拼接外部协议细节 |
| 表达业务概念和不变量 | Domain Model / Entity / Value Object | 状态、行为、领域约束 | 依赖 Controller、响应格式或数据库查询细节 |
| 跨边界转换数据形状 | DTO / Command / Query / VO / Assembler | 请求、响应、查询和模型转换 | 把持久化对象未经判断当成外部契约 |
| 承担横切或触发职责 | Validator / Scheduler / Listener / Config / Aspect | 校验、调度、事件响应、配置和横切处理 | 混入不属于自身的业务流程 |

这些名称不是固定目录要求。项目可能使用 Facade、Domain Service、Manager、Handler 或
其他命名；名称不同不代表职责不同，先看实际行为。

### Service 的边界

Service 应围绕业务用例、业务能力或稳定的应用边界组织，而不是机械地“一张表一个 Service”。
支付、取消、发货可能都修改订单，但它们未必属于同一业务能力。

反过来，也不要为了“按业务切”把一个紧密相关的用例拆成许多只转发一行的类。一个 Service
值得拆分的信号包括：职责已经互不相干、变更原因明显不同、事务边界不同、规则难以独立测试
（见「三、可测性是设计约束」），或类已经成为无关业务的聚集地。

一个只有下层调用的 Service 不是自动错误；它仍可能承担事务、权限、审计、幂等、模型转换、
稳定 API 或防腐层价值。只有在这些价值都不存在时，才应考虑删除或合并它。

### 用例编排：Service 入口的默认样式

写一个业务用例时，把 Service 的入口方法写成一段**任务编排定义**：先说第一步做什么、
第二步做什么，每步一句注释，重活交给别人，入口方法本身保持短、可整段读完。

- **形态**：入口方法体 = 编号注释 + 每步一条委托调用；方法内保留事务、步骤顺序、
  分支和返回组装。方法本身不写大段业务逻辑。
- **每步一句注释**：写出这一步做什么，必要时写为什么放在这一步。
- **三类委托目标**：
    - 其它业务 Service：承载业务规则、状态流转、跨能力协作的步骤；
    - 无状态助手 / 装配 / 校验类：纯数据转换、格式整理、规则判断；不碰数据库、不持有状态；
    - Client / Gateway：远程调用、缓存、消息等外部依赖。
- **数据处理**：一行装得下的转换（如把领域对象装配成渠道请求、字段映射）就地内联在
  对应步骤下；逻辑复杂或跨处复用的转换，抽到装配器或无状态工具类。
- **步骤粒度**：一步对应一个有明确意图的独立小任务。既不把一个步骤拆成一行转发的空壳
  方法，也不在一步里堆多条互不相关的操作。
- **例外**：项目既有风格优先；极简单的单表 CRUD 或只读查询不必强行编排。分步本身不是
  价值，顺序、事务、分支、失败处理和清晰意图才是；没有这些值的「转发」依然是无意义
  转发，不是编排。读路径的形态见「读用例的形态（查询路径）」一节。

示例（仅示意形态，命名和结构以项目邻居为准）：

```java
@Transactional
public PayResult pay(OrderPayCommand cmd) {
    // 第 1 步：校验订单状态与支付金额 —— 委托校验 Service
    Order order = orderValidator.validatePayable(cmd.orderId(), cmd.amount());
    // 第 2 步：幂等判重，防止重复支付 —— 委托无状态助手
    idempotentGuard.check(order.id(), cmd.txId());
    // 第 3 步：装配渠道请求 —— 本地数据转换
    ChannelPayRequest req = ChannelPayAssembler.from(order, cmd);
    // 第 4 步：远程调用支付渠道 —— 委托 Client
    ChannelPayResponse resp = payChannelClient.prePay(req);
    // 第 5 步：落库并返回 —— 委托 Repository
    paymentMapper.insert(resp.toPayment(order.id()));
    return PayResult.ok(resp.paymentNo());
}
```

### 读用例的形态（查询路径）

读路径是后端日常的大头，但它和编排风格是两回事：查询大多线性——取数、按需转换、返回，
不需要「第 1 步、第 2 步」式的分步编排。只读查询不必强行编排，但归属依然要清楚：

- **Controller 只做协议**：接收参数、调用查询用例、转换响应；不注入 Mapper 拼查询，
  不把持久化对象直接交给表现层。
- **查询用例 = 取数 + 组装**：取数下沉到 Mapper / Repository（或专门的读模型）；
  字段裁剪与转 VO 由 Service 或装配器完成，Controller 不负责拼装。
- **Entity 不直接成为返回契约**：默认返回 VO / DTO，把持久化结构挡在表现层之外
  （见默认原则 8）；分页返回 `Page` / `List<VO>`，不把 `Page<Entity>` 直接暴露。
  项目直接把 Entity 当契约时，按项目惯例。
- **取数一次到位**：要展示的字段、关联数据在查询时就取齐，不在循环里逐条查
  （见默认原则 7），也不在表现层 / 序列化时才触发懒加载。
- **纯读通常不加事务**：需要跨多次查询保证一致视角，或项目惯例是
  `@Transactional(readOnly = true)` 时，按项目实践加。
- **极简单的单查单回不必为每个 GET 造一个 Service**，先看邻居怎么做；只有明显越界
  （Controller 查库、Entity 裸奔）才需要收拢到 QueryService。

示例（仅示意形态，命名和结构以项目邻居为准）：

```java
@Service
public class OrderQueryService {
    public OrderDetailView detail(Long orderId) {
        // 一次取数：明细与行项查齐（不在循环里逐条查）
        OrderDetailData data = orderMapper.selectDetail(orderId);
        // 组装 VO：把持久化结构转成对外契约
        return OrderDetailAssembler.from(data);
    }
}
```

## 三、可测性是设计约束

写 Service 方法之前先问一句：**这个方法的单测要 mock 几个协作者？** 答不上来或者超过
预算，说明职责还没拆对，先拆再写。测试难写是设计问题的输出，不是测试的锅：一个只能靠
`@SpringBootTest` + 真实数据库才能验证的方法，通常意味着规则、取数、写库、组装被揉在了
同一个方法里。

### 三档预算

| 代码性质 | 目标形态 | 单测预算 |
|---|---|---|
| 纯规则：状态判定、阈值、封顶、周期键、百分比 | 无状态 policy / 纯函数，`now` 从参数传入 | **0 个 mock**，参数化覆盖边界 |
| 用例编排：校验 → 取数 → 写 → 组装 | 每步一个明确协作者 | **≤ 5 个 mock**；超过说明方法承担了多个用例 |
| 必须有基础设施：SQL 语义、事务回滚、Redis 幂等 | 单独一层，公开方法保持薄 | 交给集成测试，不硬塞单测 |

### 十条红线

1. **时间从参数或 `Clock` 取**：业务方法不出现 `new Date()`、`LocalDate.now()`、
   `System.currentTimeMillis()`；“今天”“当前季度”由入口算好传进来。
2. **业务路径不直接调静态工具**：事件用注入的 `ApplicationEventPublisher`；格式化与
   计算走注入的无状态组件。`XxxUtils.xxx()` 只允许出现在装配器或纯函数里。
3. **禁止 public 可变静态状态**：常量用 `private static final List.of(...)`，对外只暴露
   不可变视图；测试之间共享的全局可变集合会让用例顺序敏感、互相污染。
4. **构造器注入 + `private final`**：字段 `@Autowired` 只作为旧代码豁免，新代码不写。
5. **读方法不写库**：查询接口里出现 INSERT / UPDATE，就是“读 + 推进”两件事，拆成
   `xxxQuery(...)` 与 `xxxAdvance(...)`，由编排层决定何时调用；不靠“顺手建一行”省请求。
6. **一个公开方法 = 一个用例，一个类 = 一个变化原因**。软上限：类 > 500 行、
   构造依赖 > 7、入口方法 > 40 行、单方法 if/else 分支 > 5 —— 命中任意两条先拆再写。
7. **规则抽成 policy**：`resolveStatus(term, record, now)`、`threshold(i, total)`、
   `cap(value, delta, max)` 这类判定独立成类，编排层只调用；条件不复制、不内联两遍。
8. **配置只在一处解析**：入口把 JSON / Map 解析成强类型并校验，业务方法只接收对象；
   不把“字符串 → 对象 → 逐字段判空兜底”散在多个 private 方法里。
9. **null 不承担多种业务含义**：用 `Optional`、结果对象或具体异常表达“为什么不可用”；
   同一个 `return null` 对应三种原因时，调用方和测试都无从分辨。
10. **事务边界写在用例入口**：`@Transactional` 或显式 `TransactionTemplate` 放在公开
    用例方法上，不藏在私有步骤的 lambda 里；“每步独立事务”就把它变成独立的公开小用例。

### 组装与取数分离

VO 组装、字段映射、百分比换算抽成 Assembler 或无状态助手：输入是已取好的数据，输出是 VO。
组装器可以零 mock 单测；取数失败也不会污染组装逻辑。组装方法里出现第二次 Mapper 调用，
说明它其实是一个查询用例，而不是装配器。

### 改法示意

```java
// 反例：读方法里写库，规则、取数、组装揉在一起，单测要 mock 六个协作者
public VO detail(Long id) {
    Machine m = machineMapper.selectById(id);                 // 取数
    if (!m.isCoin()) return null;                             // 规则，还用 null 表达原因
    Slam s = slamMapper.selectByDay(m.id(), playerId);
    if (s == null) { s = new Slam(); slamMapper.insert(s); }  // 读方法里写库
    return copyAndFill(s);                                    // 组装里又查配置、算百分比
}

// 正例：规则零 mock、写库单独一层、入口只做编排
public VO detail(Long id) {
    Machine m = machineGate.requireCoinMachine(id);      // 取数 + 明确异常
    long award = awardPolicy.price(m.gamePrice());       // 纯规则，可参数化测试
    Slam s = dailyRecord.getOrCreate(m, playerId);       // 唯一写点，单独测
    return detailAssembler.from(s, award);               // 纯组装，零 mock
}
```

### 完成标准

- 新增纯规则类：有覆盖边界的单测，测试文件里没有任何 `@Mock`。
- 新增用例方法：单测里 `given` 不超过 5 个；超了要么拆步骤，要么把规则抽出去。
- 任何新增业务方法：不允许“必须 `mockStatic` 才能测”的写法。
- 评审时把这条当硬指标：单测文件里 stub 行数超过用例行数一半，先回头拆设计。

## 四、默认设计原则

以下是默认方向，不是脱离项目上下文的绝对禁令。

1. **主流程可读**：用例 Service 的入口方法应能当作一段带注释的步骤编排来读（见
   「用例编排：Service 入口的默认样式」一节）；复杂查询、规则判断、写库和外呼细节
   下沉到执行该步的 Service、工具类或 Client。分步的价值来自编排自身的顺序、事务、
   分支与失败处理，不为凑方法数量制造一行转发空壳方法。
2. **事务覆盖一致性边界**：单纯查询通常不需要事务；读改写、状态流转和需要原子性的多步
   写操作通常需要事务。事务位置和 `readOnly` 用法优先遵循项目实践；外部调用是否纳入事务，
   要结合锁持有时间、超时、重试和失败补偿判断。
3. **异常保留语义**：业务失败应保留业务含义，由项目统一机制翻译为接口响应。不要中途吞掉
   异常、返回 null 或默认成功。Controller 通常不负责业务异常捕获；资源清理或项目确有局部
   处理约定时，按项目惯例处理。
4. **日志可定位且安全**：关键分支和外部调用应有足够的业务标识、结果和错误现场；异常保留
   堆栈。出入参必须遵守脱敏、日志级别、大小和合规要求，不记录密码、Token 或不必要的敏感数据。
5. **分层校验**：必填和格式校验靠近入口；跨字段、跨对象和依赖当前状态的规则在业务边界
   再确认一次。不要只依赖前端校验。
6. **写接口先检查副作用**：根据需求考虑重复提交、权限、越权、并发更新、唯一约束和重试
   是否会重复产生副作用；不适用时说明原因。
7. **查询与数据量匹配**：优先批量取数、分页和按需取字段，避免循环内逐条查询；如果数据量
   很小、批量 API 不可用或项目已有其他策略，应说明取舍，而不是机械套用规则。
8. **模型边界清楚**：不要让持久化模型未经判断成为 API 契约。是否使用 DTO、VO、领域模型
   或 Entity 跨越某个边界，取决于项目架构、生命周期和已有惯例；重点是避免外部契约被数据库
   结构牵着走。
9. **稳定概念集中表达**：状态、类型、错误码、协议字段和跨类复用配置不要散落字面量。一次
   性局部文案不必为了形式强行抽常量；项目有国际化、枚举或配置规范时遵循它。
10. **依赖方向可解释**：通常是入口调用业务，业务调用数据访问或基础设施抽象；持久化和模型
    代码不应反向依赖入口层。若项目采用六边形、DDD 或其他架构，以其明确边界解释依赖方向。
11. **接口有理由才抽象**：存在多种实现、替换边界、外部契约、测试隔离或项目既有接口模式时
    再抽接口；不要为了形式制造 Interface + Impl。

## 五、改动前的职责归属说明

新增或明显改造文件时，先用简短文字说明：

| 文件 | 主要职责 / 由谁负责 | 参考邻居或依据 | 边界变化 |
|---|---|---|---|
| `OrderController` | 接入层：接收请求并调用用例 | `OrderQueryController` 的响应和校验方式 | 不承载支付规则 |
| `OrderPayService` | 业务层：编排支付用例 | `OrderQueryService` 的事务和异常风格 | 新增支付业务边界 |
| `OrderPayMapper` | 数据层：支付记录持久化 | 同模块已有 Mapper | 不新增业务判断 |

“邻居”应尽量指向实际类或文件；如果没有直接邻居，写明查过的依据和为什么这样定职责归属。
只修改一两个文件时，一句话说明即可，不要求为了形式制作表格。

这段说明的落点：局部档就是对话里短设计的一部分（怎么做、碰哪儿、怎么验证）；架构档
写进设计文档 / 实施计划，`implement` 进入实现后会把放置位置结论记进计划文件。

## 六、常见误区

| 念头 | 更稳妥的判断 |
|---|---|
| “项目分层不清楚，我自己设计一套” | 先从包结构、调用链和邻居读取项目语言；证据不足就询问 |
| “Controller 里顺手写一点业务判断” | 判断是否依赖业务状态；依赖业务状态的规则通常应回到业务边界 |
| “建 `XxxService + XxxServiceImpl` 更规范” | 先确认是否存在替换、多个实现或项目既有模式 |
| “一个表一个 Service 最清楚” | 先看业务动作和变更原因，表通常不是业务边界 |
| “为了整洁把一件事拆成五个类” | 优先拆出有独立职责或边界的步骤，不要制造空壳类 |
| “Service 只做转发就没价值” | 有真实编排价值的转发（顺序、事务、分支、失败处理、清晰意图）不是无意义转发；无意义转发指没有任何决策与值的转发 |
| “每步都要拆成一个 private 方法” | 步骤委托给其它 Service / 工具类 / Client，入口方法内联注释分步；只有单步复杂到影响阅读才抽 helper |
| “Entity 直接返回最省事” | 先确认它是否会把持久化结构变成外部契约 |
| “查询 Service 没用，Controller 直接查 Mapper 就好” | 查库与暴露 Entity 进 Controller 是越界；需要组装 VO、屏蔽持久化结构、跨源拼装时，薄 QueryService / 读模型正当；纯透传按邻居定 |
| “所有查询都必须批量、所有文案都必须常量化” | 先看数据规模、复用范围和项目约定，记录必要的例外 |
| “邻居这样写，所以我照抄” | 邻居是证据，不是免检；同时检查它是否存在越界或遗留问题 |
| “读接口里顺手建行、推进进度，省一次请求” | 读接口写库会把查询用例变成写用例；拆成显式推进步骤，由编排层决定何时调用 |
| “用 `new Date()` 就行，测试自己控制不了时间” | 时间不可注入意味着跨天、跨年、窗口边界永远测不到；从参数或 `Clock` 取 |
| “发个事件而已，`SpringUtils.publishEvent` 最快” | 静态发布无法 mock、无法断言副作用；注入 `ApplicationEventPublisher` 同样一行 |
| “配置 JSON 在 Service 里解析，省一个类” | 解析散落会让每个方法都要逐字段判空兜底；入口解析成强类型，业务只认对象 |
| “测试写不动就先上集成测试兜底” | 集成测试兜的是 SQL 与事务语义；规则和编排写不动，先按「三」拆设计 |

## 七、做出判断时的最小顺序

1. 找到同模块或相近模块的邻居。
2. 说清楚这段代码的主要职责、输入输出和副作用。
3. 判断它属于哪个现有边界，或是否确实需要新边界。
4. 对照邻居保持命名、异常、事务、映射和测试风格。
5. 检查是否存在越界、重复副作用、并发、敏感数据或查询规模问题。
6. 核对用例入口是否可读作带注释的分步编排，每步是否由明确的 Service / 工具类 /
   Client 承担；读路径核对 Controller 是否只做协议、QueryService 取数并组装 VO。
7. 算一遍单测账：规则能不能零 mock 测、用例方法要几个 `given`、有没有静态调用或
   隐式时间挡路；不达标先拆，不进入实现。
8. 如果偏离默认原则，说明为什么、替代方案是什么、代价是什么。

本技能的目标不是让所有代码看起来一样，而是让每个职责归属和拆分决定都有业务依据、项目依据
和可解释的边界。
