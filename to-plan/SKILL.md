# 成文：实施计划

设计文档说**要什么**，实施计划说**按什么顺序做出来**。

计划文件同时是这次工作**唯一的进度记录**：做到哪儿、卡在哪儿、一路上裁决了什么，都记在它里面，不记在脑子里。

<HARD-GATE>
写完给用户逐任务过一遍、拿到签字之前，不许开工。
</HARD-GATE>

## 流程

1. 读设计文档。**计划从它论证出来**——计划里任何一条与设计文档冲突，以设计文档为准，并且**把冲突报出来**。
2. 切任务（见下）。
3. 写进 `docs/plans/<slug>.md`（目录按需创建），在文件开头记下所依据的设计文档路径，把路径报给用户。
4. 自检（见下），发现问题就地改。
5. 跟用户逐任务过一遍，拿到签字（关卡 3）。

## 切任务的规则

**一个任务 = 自带验证、且值得单独被评审一次的最小单位。**

- 设置、脚手架、文档、配置这类步子，**折进需要它的那个任务**，不要单独成任务。
- 只在「评审者可能单独否掉 A 却通过 B」的地方切开。
- 拿不准就切粗一点：任务太碎，每个任务的上下文重建比干活本身还贵。
- 第一个任务就是第一个，**不要有「任务 0：搭好环境」**。

## 每个任务的写法

```markdown
### 任务 1：<交付物名字>   `[ ]`

**交付物**：做完之后，什么东西存在了。

**要碰的位置**：文件、接口、语句、配置项的名字——**只列名字，不贴代码**。
这些是导航用的，不是规范；干的过程中发现还要碰别处，就地补进来。

**覆盖验收**：设计文档里第 3、7 条

**验证**：跑什么、看什么、或者核对什么。**必须是一条你能实际执行的检查**，
不能写「确认没问题」这种话。
```

**状态字段**写在任务标题行末尾：

| 标记 | 含义 |
|---|---|
| `[ ]` | 未开始 |
| `[~]` | 进行中 |
| `[x]` | 已完成 |
| `[!]` | 卡住（在任务下面写一行原因） |

## 纪律

- **计划文件是唯一的进度记录。** 上下文被压缩之后，以计划文件 + 版本历史为准，**不许重跑已完成的任务**——这是这类流程里最贵的失败。
- **没有占位符。** 每个任务都要有交付物、位置、验证。出现「待定」「同上」「细节后续补」，就是没写完。
- **不做设计文档没要求的事。** 想加，先回头改设计文档，别在计划里偷偷加。
- **任务之间不许互相打架。** 前一个任务产出的东西，后一个任务假设它存在的方式要对得上。
- **裁决也记在这里。** 实施过程中你自己拍板的决定，写成一行 `裁决：<决定了什么> — <为什么> — <错了的话代价是什么>`。

## 自检

- 设计文档的每一条验收，**至少被一个任务覆盖**——把没覆盖到的列出来补上。
- 每个任务的验证项，**你自己真的执行得动吗**？执行不动的（比如要别人的环境），在任务里写明由谁做、怎么做。
- 任务之间有没有引用不存在的东西？
