# 开工：定档与编排

任何要动手改代码的请求，先定档，再动手。**随任务简单而缩水的是产出物，永远不是批准。**

这是一条流程链的入口。定档决定这条链走多长，以及在哪几个地方必须停下来等人。

## 先分流

不是所有请求都该进这条链。先按请求类型分流，再谈定档：

| 请求 | 走 |
|---|---|
| 新增、修改、重构代码，或说「开工」「开始做」 | 本技能 |
| 报错、测试失败、行为不符预期，先查根因 | `debugging`（定位后再回来定档） |
| 只评审分支、PR 或进行中的改动 | `code-review` |
| 只想压测思路，明确不打算动手 | `grilling` |
| 只问「做完了吗 / 通过吗 / 修好了吗」 | `verification` |

分流之后仍要动手的，再回到本技能定档。调试定位到根因后要修，也一样回来重新定档。

## 第零步：加载输出协议

开工前先用 `Skill` 工具加载 `discuss-mode`（加载协议不算动手），本链全程按它的输出协议说话。风格冲突以它为准，流程与关卡以本技能为准。链上后续的 `to-spec`、`to-plan`、`implement` 也由本技能按关卡加载，不要求用户手动点名。

加载不到就在第一条回复里说明，不要默默跳过——`discuss-mode` 是本技能的前置依赖，两个技能必须装在一起。

仓库根如果有 `CONSTRAINTS.md`，也读了它——那是这个仓库「绿」的定义，本链每个「声称通过」的点都以它为准（见 `constraints`）。没有就先记下，**不要在定档阶段新建**；等第一次需要跑验证时，由 `constraints` 走首次创建流程。

<HARD-GATE>
在你把意图说出来、并拿到用户明确同意之前：不写任何代码，不新建文件，不调用任何实现类技能。
局部档也要过这道关卡——设计可以是三句话，同意必须是明确的。
</HARD-GATE>

## 第一步：定档

在说第一句澄清的话之前定档，并且**把档位说出来**，让用户可以当场否决。

| 档 | 判定规则 | 产出物 |
|---|---|---|
| **试验档** | 问的是「能不能 / 可不可行」，或用户明说「先试试、快糙猛就行」。产出是**一个答案，不是要留下来的代码** | 一句结论 + 建议 |
| **局部 Bounded** | **你要改的那段流程，在你的仓库里已经存在、读得到** | 对话里的一段短设计 |
| **架构 Architectural** | 新项目、新子系统、改变组件之间怎么拼、动了别人依赖的接口 | 设计文档 + 实施计划 |

### 局部档要过的检查：**指出位置**

判定的动作是一句话：**「我要改的是 <具体位置> 那段。」**

- 指得出位置 → 局部
- 指不出（还不存在，或者要新建）→ 架构
- 问的是「能不能」 → 试验档

局部量的是**仓库**，不是你的熟悉程度：在一个从没见过的老项目里加个小参数仍然是局部；在自己最熟悉的业务里新建子系统仍然是架构。判定的对象是**请求**，不是你的信心。

## 写代码前的加载

两个配套技能影响的东西不同，加载时机也不同；都只加载一次。

| 技能 | 什么时候加载 | 判据 |
|---|---|---|
| `spring-boot-conventions` | 定档后、写短设计（局部）或设计文档（架构）之前 | 仓库有 Spring Boot（`@SpringBootApplication`、`spring-boot-starter-*`），且这次改动碰后端代码：Controller / Endpoint / Service / Use Case / Repository / Mapper / Entity / DTO / VO / Client，或要拆的大方法、大类 |
| `ponytail` | 进入实现之前（局部第 5 步、架构 `implement` 之前） | 这次要留下代码。试验档不加载：它的产出是一次性答案 |

拿不准后端判定时，先读 `pom.xml` / `build.gradle` 和包布局；判定的结论，局部档写进短设计，架构档写进计划文件。

`ponytail` 默认 `full`，用户点名 `lite` / `ultra` 才切换；加载这些技能只是读判断依据，不算动手。

`ponytail` 管的是**构建什么、写多少、验证写不写**，不压缩：局部档短设计或架构档计划确定的范围、`tdd` 的红→绿节奏、`constraints` / 任务验证项，以及收尾报告。它只压缩实现本身。

加载不到就在对话里说明，并按最小实现底线或项目现有约定自行约束；不要默默假装按它做过。`implement` 被直接调用时，也按本节补载。

## 三条路

### 试验档
1. 把问题和打算怎么试，用两三句话说清楚
2. 拿一个点头
3. 用最省的方式查
4. 报结论——是建议，不是交付；试出来的东西一律标注为一次性

不写设计文档，不写实施计划。

### 局部
1. 只读够判断的上下文
2. 用 `grilling` 问**真正要紧的**那几题（一轮就够，不必问到最后没有可问的问题）
3. 碰后端就先按「写代码前的加载」加载 `spring-boot-conventions`；然后在**对话里**给一段短设计：怎么做、碰哪儿、怎么验证
4. **停下来，等明确的「同意」**——把设计说出来和动手做，不能是同一句话
5. 进入实现前按「写代码前的加载」加载 `ponytail`，然后直接实现（`tdd` 照用）。分工：`ponytail` 决定验证写不写、写多大（平凡免测、非平凡至少一个可运行检查），`tdd` 决定需要验证时的红→绿节奏（见 `tdd` 的「与 `ponytail` 的分工」）；免测不等于跳过验证，交付前仍过 `verification`。不写文档，不写计划
6. 交付前过 `verification`

### 架构
1. 只读现有的 `CONTEXT.md`、ADR 和代码；可用 `codebase-design` 的词汇分析，但不修改任何文件
2. `grilling`——问到没有可问的问题
3. 碰后端就先按「写代码前的加载」加载 `spring-boot-conventions`；然后在对话里总结谈定的意图、边界和准备产出的文档
4. **关卡 1：停下来等用户明确批准开工**
5. 批准后再用 `domain-modeling` 落盘——术语与不变量进 `CONTEXT.md`，决策进 ADR
6. `to-spec`——出**设计文档**
7. **关卡 2：用户评审设计文档**
8. `to-plan`——出**实施计划**
9. **关卡 3：用户对计划签字**
10. 先按「写代码前的加载」加载 `ponytail`，再用 `implement`——逐任务执行；此后编排权交给计划文件
11. `verification`——先拿证据；再 `code-review`——两个维度的评审

## 档位只能升，不能降

1. **拿不准就走重的。**
2. **中途发现更复杂** → 停下来说一声，升级路径。
3. **不许中途降级。** 写着写着觉得「其实挺简单」，也走完已经声明的路径。
4. **每个任务各自定档、各自批准。** 试验档跑通了想留下代码，那是一个**新请求**，重新定档。刚才批过试验档 ≠ 后续改动也批过了。

## 三个关卡

| 关卡 | 位置 | 怎么过 |
|---|---|---|
| 1 开工批准 | 所有档，动手之前 | 用户明确说同意 |
| 2 设计文档评审 | 架构档，`to-spec` 之后 | 用户读文档 |
| 3 实施计划签字 | 架构档，`to-plan` 之后 | 用户逐任务过一遍 |

过了关卡 3 就不再设关卡：**提交与集成由用户自己决定**，你只需要报告并停。

## 编排：链长随档位变

| 档 | 链 |
|---|---|
| 试验档 | 出题 → 点头 → 试 → 报结论（不写文档、不写计划） |
| 局部 | 轻量 grilling → 短设计 → 同意 → 实现（tdd）→ verification |
| 架构 | grilling → 总结意图 → 批准 → domain-modeling → to-spec → 评审 → to-plan → 签字 → implement → verification → code-review |

局部档与架构档都要在写设计前、进入实现前，分别按「写代码前的加载」加载配套技能；局部档和试验档不跑 `code-review`；两个维度评审是架构档的收尾。

**进入 `implement` 之后，编排放手**：接下来做哪个任务，由实施计划文件承载。

## 单独入口：调试

「查这个 bug 的根因」不属于这三档——走 `debugging`。定位到具体缺陷之后，**再对「修它」这件事定一次档**。

## 念头 → 现实

| 念头 | 现实 |
|---|---|
| 「这个太简单了，不用设计」 | 简单意味着**短**设计，不是**没**设计 |
| 「先看一眼代码再定档」 | 读代码不算动手；但档位要在**提第一个问题之前**说出来 |
| 「先把架子搭起来，设计边做边定」 | 那是没批准就动手 |
| 「他说了随便你怎么弄」 | 那是把设计责任交给你，不是免除批准 |
| 「设计已经说出来了，他应该会同意的」 | 批准是**等到的**，不是推断出来的 |
| 「它变复杂了，但我快做完了」 | 档位只能升不能降：停下来说，走升级路径 |
| 「测试红了，把阈值调低、或者加个 @Disabled 就绿了」 | 那是改底线，不是改代码。放松必须出声（见 `constraints`） |
| 「试验档跑通了，代码我留着用」 | 试验档的产出是答案；留代码是新请求，重新定档 |
| 「刚才批准过，后面的改动顺带算批过了」 | 每个任务各自定档、各自批准 |
| 「只是查个 bug / 评审一下」 | 走 `debugging` / `code-review`，别启动这条链 |
| 「配套技能等 implement 时再载」 | 局部档不经过 implement，会漏掉；按「写代码前的加载」提前载 |
| 「ponytail 载早了，设计也按三行说」 | ponytail 只管写多少；短设计、关卡和收尾报告不受它压缩 |
| 「discuss-mode 没装，这次先跳过」 | 前置依赖缺失要报出来，不是默默降级 |
