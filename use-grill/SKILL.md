# 开工：定档与编排

任何要动代码的请求，先定档，再动手。**随任务简单而缩水的是产出物，永远不是批准。**

这是一条流程链的入口。定档决定这条链走多长，以及在哪几个地方必须停下来等人。

## 第零步：加载输出协议

开工前先用 `skill` 工具加载 `discuss-mode`（加载协议不算动手），本链全程按它的输出协议说话。风格冲突以它为准，流程与闸门以本技能为准。

加载不到就在第一条回复里说明，不要默默跳过——`discuss-mode` 是本技能的前置依赖，两个技能必须装在一起。

仓库根如果有 `CONSTRAINTS.md`，也读了它——那是这个仓库「绿」的定义，本链每个「声称通过」的点都以它为准（见 `constraints`）。**没有就不用管，别顺手新建一个。**

<HARD-GATE>
在你把意图说出来、并拿到用户明确同意之前：不写任何代码，不新建文件，不调用任何实现类技能。
局部档也要过这道闸门——设计可以是三句话，同意必须是明确的。
</HARD-GATE>

## 第一步：定档

在说第一句澄清的话之前定档，并且**把档位说出来**，让用户可以当场否决。

| 档 | 判定规则 | 产出物 |
|---|---|---|
| **探针 Spike** | 问的是「能不能 / 可不可行」，或用户明说「先试试、快糙猛就行」。产出是**一个答案，不是要留下来的代码** | 一句结论 + 建议 |
| **局部 Bounded** | **你要改的那段流程，在你的仓库里已经存在、读得到** | 对话里的一段短设计 |
| **架构 Architectural** | 新项目、新子系统、改变组件之间怎么拼、动了别人依赖的接口 | 设计文档 + 实施计划 |

### 局部档要过的检查：**指出位置**

判定的动作是一句话：**「我要改的是 <具体位置> 那段。」**

- 指得出位置 → 局部
- 指不出（还不存在，或者要新建）→ 架构
- 问的是「能不能」 → 探针

局部量的是**仓库**，不是你的熟悉程度：在一个从没见过的老项目里加个小参数仍然是局部；在自己最熟悉的业务里新建子系统仍然是架构。判定的对象是**请求**，不是你的信心。

## 三条路

### 探针
1. 把问题和打算怎么试，用两三句话说清楚
2. 拿一个点头
3. 用最省的方式查
4. 报结论——是建议，不是交付；试出来的东西一律标注为一次性

不写设计文档，不写实施计划。

### 局部
1. 只读够判断的上下文
2. 用 `grilling` 问**真正要紧的**那几题（一轮就够，不必问到前沿为空）
3. 在**对话里**给一段短设计：怎么做、碰哪儿、怎么验证
4. **停下来，等明确的「同意」**——把设计说出来和动手做，不能是同一句话
5. 直接实现（`tdd` 照用）。不写文档，不写计划
6. 交付前过 `verification`

### 架构
1. 读上下文（`domain-modeling`、`codebase-design` 从这里起）
2. `grilling`——问到前沿为空
3. `domain-modeling`——术语与不变量进 `CONTEXT.md`，决策进 ADR
4. `to-spec`——出**设计文档**
5. **闸门 2：用户评审设计文档**
6. `to-plan`——出**实施计划**
7. **闸门 3：用户对计划签字**
8. `implement`——逐任务执行；此后编排权交给计划文件
9. `code-review` + `verification`

## 棘轮：只能往上升

1. **拿不准就走重的。**
2. **中途发现更复杂** → 停下来说一声，升级路径。
3. **不许中途降级。** 写着写着觉得「其实挺简单」，也走完已经声明的路径。
4. **每个任务各自定档、各自批准。** 探针跑通了想留下代码，那是一个**新请求**，重新定档。刚才批过探针 ≠ 后续改动也批过了。

## 三个闸门

| 闸门 | 位置 | 怎么过 |
|---|---|---|
| 1 开工批准 | 所有档，动手之前 | 用户明确说同意 |
| 2 设计文档评审 | 架构档，`to-spec` 之后 | 用户读文档 |
| 3 实施计划签字 | 架构档，`to-plan` 之后 | 用户逐任务过一遍 |

过了闸门 3 就不再设闸门：**提交与集成由用户自己决定**，你只需要报告并停。

## 编排：链长随档位变

| 档 | 链 |
|---|---|
| 探针 | 出题 → 点头 → 试 → 报结论 |
| 局部 | 轻量 grilling → 短设计 → 同意 → 实现 |
| 架构 | grilling → domain-modeling → to-spec → 评审 → to-plan → 签字 → implement → code-review |

**进入 `implement` 之后，编排放手**：接下来做哪个任务，由实施计划文件承载。

## 旁路：调试

「查这个 bug 的根因」不属于这三档——走 `debugging`。定位到具体缺陷之后，**再对「修它」这件事定一次档**。

## 念头 → 现实

| 念头 | 现实 |
|---|---|
| 「这个太简单了，不用设计」 | 简单意味着**短**设计，不是**没**设计 |
| 「先看一眼代码再定档」 | 读代码不算动手；但档位要在**提第一个问题之前**说出来 |
| 「先把架子搭起来，设计边做边定」 | 那是没批准就动手 |
| 「他说了随便你怎么弄」 | 那是把设计责任交给你，不是免除批准 |
| 「设计已经说出来了，他应该会同意的」 | 批准是**等到的**，不是推断出来的 |
| 「它变复杂了，但我快做完了」 | 棘轮单向：停下来说，升级路径 |
| 「测试红了，把阈值调低、或者加个 @Disabled 就绿了」 | 那是改底线，不是改代码。放松必须出声（见 `constraints`） |
| 「探针跑通了，代码我留着用」 | 探针的产出是答案；留代码是新请求，重新定档 |
| 「刚才批准过，后面的改动顺带算批过了」 | 每个任务各自定档、各自批准 |
| 「discuss-mode 没装，这次先跳过」 | 前置依赖缺失要报出来，不是默默降级 |
