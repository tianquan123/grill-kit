# 验证：证据先于断言

**核心原则：先拿证据，再下结论。**

## 铁律

```
没有当次跑出来的新鲜证据，不许声称完成、修好、或者通过。
```

如果你在这一条消息里没有真的跑过那条命令、或者没有真的逐条核对过，你就不能声称它通过。**违反字面，就是违反精神。**

## 闸门函数

给出任何状态判断之前，走这五步：

1. **指名**：哪一条命令、哪一次核对，能证明这个结论？这条命令应当来自仓库的 `CONSTRAINTS.md` 命令表（见 `constraints`）。仓库没有 `CONSTRAINTS.md` 时，先加载 `constraints` 走首次创建；有文件但命令表里没有这条命令，先补进表里再谈验证。
2. **执行**：完整地执行它（新鲜的，不是上次的）
3. **读结果**：读完输出，看退出码，数失败数
4. **比对**：输出确实支持这个结论吗？
   - 不支持 → 说出真实状态，**附上证据**
   - 支持 → 说出结论，**附上证据**
5. **然后才**开这个口

跳过任何一步，那不是验证，是编。

## 常见偷懒对照表

| 声称 | 需要什么 | 什么不算 |
|---|---|---|
| 测试通过 | 完整跑完，失败数 0，**且这条 diff 没有放松底线** | 加 @Disabled、调低阈值、删断言换来的绿 |
| 编译通过 | 编译命令退出码 0 | 静态检查通过、看着没问题 |
| bug 修好了 | 复现原症状的用例现在通过 | 改了代码，假设修好了 |
| 回归验证有效 | 反证过：去掉修复它必须失败 | 它通过了一次 |
| 需求达成 | 逐条对着验收清单核对 | 测试绿了 |
| 别人干完了 | 看版本历史里的实际改动 | 他自己报告「成功了」 |

## 无法执行验证的时候

有些环境里，**验证命令就是跑不起来**（依赖拿不到、环境不在手上）。这不是省略验证的许可，只是换一条路：

1. **说出来。** 明确讲：「这条我没能跑，因为 <原因>。」
2. **换替代证据。** 能做的静态核对要做足：逐条对着验收清单走查、核对必须两处同步的定义、检查分层与命名约定、看有没有没处理到的路径。
3. **标注等级。** 报告里把结论分成两类：**已验证**（附证据）与**未验证**（附原因，以及建议谁来跑、怎么跑）。
4. **不越界。** 任何情况下都不许把「没跑」写成「通过」，也不许用「应该没问题」这类措辞顶替结论。

**没验证，就说没验证——这本身就是一个合格的结论。**

## Red Flags

- 出现「应该」「大概」「看起来没问题」
- 还没核对就先表达满意（「好了」「搞定」）
- 拿静态检查的结果去证明编译通过
- 相信别人（或者子代理）的成功报告，没看实际改动
- 「就这一次，特殊处理」
- 「差别不大，部分核对就够了」
- 累了、想收工了

## 何时适用

**只要你要说下面任何一句，就先过闸门**：

- 任何形式的「完成 / 通过 / 修好 / 没问题」
- 任何表达满意的句子
- 提交、开 PR、交接、进入下一个任务之前
- 派活给别人，或者采信别人的回报之时

适用于：原话、同义改写、暗示，以及任何听起来像「这事成了」的措辞。
